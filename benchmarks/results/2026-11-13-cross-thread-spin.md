# 验收修订：跨线程投递路径（bridge_cross_thread），2026-11-13

## 归因（修改前，提交 269e08f）

工具：自建微基准 /tmp/xb（与 aw-bench / asio-bench 的 bridge_cross_thread 代码相同，只跑这一项）。

- 用 steady_clock 在三处打点：
  - 发起：协程调用 `completer.submit`；
  - 完成线程开始执行 job；
  - job 的 dispatch 返回。
- 用 `/proc/self/task/*/status` 读每个线程的自愿与非自愿切换次数。
- strace（免 root 的 Debian 包，用 `dpkg -x` 解出）只用于数系统调用。strace 会打乱时序，所以只作参考。

单核（`taskset -c 2`），每次运算：

| | 总耗时 | 发起 → 完成线程开始 | 完成线程投递 | 投递 → 协程恢复 | 池线程切换（自愿/非自愿） | 完成线程切换（自愿/非自愿） |
| --- | --- | --- | --- | --- | --- | --- |
| aw 修改前 | ≈4750 ns | 3765 ns | 96 ns | 888 ns | 0 / 1.94 | 1.94 / 0 |
| aw 修改后 | ≈3200 ns | 2259 ns | 90 ns | 855 ns | 0 / 1.95 | 1.95 / 0 |
| asio | ≈3390 ns | 2260 ns | 783 ns | 1909 ns | 0.97 / 0.97 | 1.28 / 0.66 |

结论：

- 差距全部在“发起 → 完成线程开始”这一段。池线程 submit 以后进入搜索：先做 10 轮指数退避的 pause 自旋，一共 1023 次 pause，本机每次约 11.3 ns，合计约 11.6 µs；之后再让出 2 次时间片。
- 只有 1 个 CPU 时，被唤醒的完成线程必须等池线程让出这个核才能运行，所以这段 pause 只是在推迟它。池线程从来不停车（自愿切换 0 次），每次运算都是被抢占或在 yield 时让出（非自愿切换约 2 次）。
- aw 的投递本身（约 90 ns，全局队列加锁一次，池线程在搜索中，不用唤醒）和恢复（约 0.9 µs）都比 asio 快。asio 的池线程睡在条件变量上，投递时要 signal，恢复时要再经过一次 futex 往返。
- 切换总次数两边相当，每次运算 aw 约 3.9 次，asio 约 3.8 次。
- strace 计数（受 strace 干扰，只作参考），每次运算：aw 修改前 futex 约 4.3 次、sched_yield 约 0.25 次；修改后 futex 约 5.0 次、sched_yield 约 0.005 次；asio futex 约 5.4 次。
- 双核时 pause 自旋有用：完成线程在另一个核上并行运行，池线程在自旋中直接拿到工作，不必停车。实验中直接去掉自旋，双核从约 6.0 µs 变成约 9–10 µs。

## 修改

工作线程启动时读取自己的 CPU 亲和性（`sched_getaffinity`）：只有 1 个 CPU 时跳过 pause 自旋，搜索直接从让出时间片的两轮开始；有 2 个及以上 CPU 时行为不变。
